# NAVFIT98A validation compared with Swift NAVFIT r109

## Result and scope

There are useful checks to add, but the highest-value change is to make Swift's live report findings, group findings, saved checklist and export readiness agree. More native rules alone will not resolve their current differences.

This is an investigation, not an application change. r109 remains the baseline. No workspaces were edited, no NAVFIT reports were validated or printed at runtime, and no new Navy-compliance claim is made.

Inspected NAVFIT98A V33 Patch 2, assembly **2.2.0.332**, SHA-256 `5366f1c1bb147f1706094c5e3e1d62981f34fc6cb301e4006a892acfbfab58cf`, MVID `74a3c3b5-a7af-48bc-ac92-963eb5331ff0`. Used installed **REA CLI 6.5.0**, without installing packages or changing MCP configuration. The live chat has no REA MCP tools; the installed CLI performed the analysis.

REA recovered **91 methods in ValidationModule**: **32 ReportCheck methods**, **49 FolderCheck methods**, two validation entry points and eight other logging/calculation/name/status helpers. These counts are methods, not independent policy-rule counts. Exact method inventory, messages, calls, locations and current Swift source hashes are in [the evidence ledger](NAVFIT_VALIDATION_REA_2026-10-14.json).

## Native execution paths established statically

- Main-window report/folder validation handlers open the native validation form. `NF_Validate.CmdStart_Click` (`0x06000f61`) calls either `NF_ValidateReport` (`0x06000f66`) or `NF_ValidateFolder` (`0x06000f89`). These are actual call edges, not conclusions from method names alone.
- Report validation reads the selected saved row from `Reports`, calls its field/relationship checks, logs failures and calls `ReportIsValidated` (`0x06000fbd`), which updates `Reports.isValidated`. That native flag is distinct from Swift's local approval.
- Folder validation reads reports by `Parent`, performs a field-check phase, then a consistency and summary phase. It repeatedly reopens readers for individual checks. It is not simply a call to report validation for each report: the paths contain different checks and special handling. Swift should share rule definitions and evaluate one collected group context, rather than reproduce those repeated queries.
- Periodic dates are not entirely in the executable. `ProceduresModule.IsPeriodicToDate` (`0x06000531`) reads the companion data database's `PerDates` table using component/class and worn paygrade, with additional special-case logic.

## Native behavior that should not become an unconditional policy rule

1. **Whole NOB presentation and summary fields.** Native rules/messages use native NOB codes and zero summary values. The supplied CH-2 compilation, enclosure (2), block 16, printed 1-5 / PDF 34, requires blank printed traits, career recommendations and summary, and NOB promotion recommendation. Storage code 0 versus printed blank must be tested separately. Do not populate visible fields to appease an internal code check.
2. **Billet subcategory.** Native NOB checks explicitly expect NA. The current block-21 instructions include blank/applicability rules (printed 1-7 / PDF 36; code table on 1-8 / PDF 37). Preserve the instruction-based user representation and investigate exact export compatibility rather than silently forcing NA.
3. **Period longer than 15 months.** Native DateDiff15MonthsElegible contains rank/designator-specific exemptions and VB month-difference logic. Current chapter 3-2, printed 3-1 / PDF 70, allows longer regular periods only with PERS-32 approval. Swift's review warning is more defensible than either blanket rejection or blindly inheriting old exceptions.
4. **Periodic exceptions.** Native IsPeriodicToDate includes a CMDCS/NOV15 special case and companion catalogue lookup. CH-2 chapter 3-4 has newer command-senior-enlisted exceptions (printed 3-2 / PDF 71 and following). New checks need dated schedules and documented exceptions, not an undated copy of PerDates.
5. **Narrative adequacy.** Native nonempty comments can satisfy its presence check. Neither native nor Swift can establish substantive justification, referral, appropriateness or verified printed fit from text presence.
6. **Grouping is not raw equality everywhere.** Native converts rates to paygrades and groups officer designators by category in its consistency routines. Swift already has deliberate UIC/active-reserve/category review. Do not reject different ratings within the same paygrade or replace these judgments with raw-string matching.
7. **Name formatting is form-specific.** Chief structured fields differ from legacy full strings. Validate/export what the current form actually stores and prints, retaining separate display names and background export components.

## Recommended implementation order

1. **One validation result across workflows.** Shared rule evaluation for report and group live views, saved readiness/checklist and export preflight. Keep atomic draft saves permissive; show incomplete, invalid, policy and needs-review findings distinctly. Every true policy rule gets a verified instruction/page/paragraph/excerpt; native-only rules identify assembly version/method and say compatibility, not Navy policy.
2. **Deterministic missing-data and relationship checks.** Add blocks 28/29, applicable physical readiness and retention, required-empty adverse comments, secondary recommendation without primary, rater/senior-rater and concurrent RS checks, RS contact completeness and missing live RS consistency findings. Include form-specific applicability before surfacing errors.
3. **Dated catalogue-driven checks.** Periodic schedule/exceptions, rank/rate/designator/warfare and senior grade/service compatibility. Unknown/currently unsupported catalogue cases are review findings, not fabricated failures.
4. **Native package reconciliation tests.** Verify generated summary counts, NOB presentation, invalid/valid boundary cases and both native report and folder validation paths for all three forms. Include synthetic imported native-only values. This audit establishes static behavior; it is not that runtime parity proof.
5. **Leadership-oriented continuity warnings.** Compare known prior regular report dates and detect likely duplicates/gaps/overlaps; incomplete historical records remain explicit. This is an additional Swift opportunity, not a discovered native rule.

Existing saved rule pack is only five checks and declares an effective end date of 3 October 2026 (`modValidation.bas`). Live checks are much broader and use the current system date as the upper policy window. This discrepancy should be resolved before presenting either as a complete readiness result. Group export likewise enforces storage/shared-value safeguards but does not call ValidateLiveGroup. A draft can therefore save or export while live findings remain; that is a workflow difference, not proof that every finding should block export.
